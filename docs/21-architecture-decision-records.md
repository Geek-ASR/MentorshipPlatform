# 21 — Architecture Decision Records

Status: Draft v0.1 · 2026-09-17 · Format: Problem → Options → Trade-offs → Decision → Reason → Revisit when.

New ADRs are appended; superseded ADRs are marked, not deleted.

### ADR-001 — Modular monolith on Next.js (App Router) with TypeScript
- **Problem:** One small team, ₹0 budget, SEO-critical public pages, complex transactional domain.
- **Options:** (a) Next.js monolith; (b) SPA + separate API service; (c) microservices; (d) React Router v7 framework.
- **Trade-offs:** (a) single deploy, SSR, one language; framework churn and CVE exposure. (b) poor SEO, two deploys. (c) operational overload. (d) portable and simpler, smaller SEO ecosystem.
- **Decision:** (a), with a framework-independent domain layer and enforced module boundaries.
- **Reason:** fastest path to SEO + full-stack with an extraction path preserved.
- **Revisit when:** multiple teams need independent deploys, or framework constraints block runtime needs.

### ADR-002 — PostgreSQL as the single system of record; Drizzle ORM; no browser-side DB access
- **Problem:** Double-booking prevention, money integrity, relational taxonomy, search.
- **Options:** Postgres; Firestore; SQLite/D1; MongoDB.
- **Trade-offs:** Postgres offers exclusion constraints, transactions, FTS and check constraints. NoSQL options push invariants into application code.
- **Decision:** Postgres; Drizzle for typed queries + reviewed SQL migrations; all access server-side.
- **Reason:** Invariants enforced in the database; portable across vendors.
- **Revisit when:** never for the core; add specialised stores (search, cache, warehouse) alongside.

### ADR-003 — Supabase Free as MVP Postgres host (used as plain Postgres + S3 storage)
- **Problem:** ₹0 managed Postgres with storage and scheduling.
- **Options:** Supabase Free; Neon Free; self-host; Firebase.
- **Trade-offs:** Supabase gives always-on compute while active, bundled storage and `pg_cron`/`pg_net`, but pauses after 7 idle days and has no backups. Neon gives a 6 h restore window and branching, but compute-hour limits conflict with minute-level job ticks and it has no storage.
- **Decision:** Supabase Free (region Mumbai) with the Data API disabled, `app` schema, no Supabase Auth; nightly encrypted offsite dumps. Neon is the documented alternative.
- **Reason:** Fewest vendors for MVP; exit cost ≈ 1–2 days.
- **Revisit when:** live money (→ paid plan with PITR) or if pausing/limits hurt the beta.

### ADR-004 — Better Auth for authentication (database sessions)
- **Problem:** Secure auth with instant revocation for bans, no per-user cost, data ownership.
- **Options:** Better Auth; Supabase Auth; Auth.js; Clerk; Firebase Auth.
- **Trade-offs:** Better Auth: we own more security surface, library risk. Supabase Auth: JWT revocation lag, vendor schema. Auth.js: maintenance mode (Sep 2025). Clerk: vendor lock-in, cost at scale.
- **Decision:** Better Auth with DB sessions, Argon2id, TOTP, strict config, pinned versions.
- **Reason:** Revocation semantics match T&S needs; zero marginal cost; portable.
- **Revisit when:** enterprise SSO needs exceed plugin capabilities, or a serious unpatched vulnerability appears.

### ADR-005 — Payment provider abstraction with Razorpay Route as primary; FakeGateway for dev/tests
- **Problem:** Marketplace split payments in India under RBI PA rules; ₹0 development; testable failure modes.
- **Options:** Razorpay Route; Cashfree Easy Split; Stripe Connect; collect-then-payout from own account.
- **Trade-offs:** Stripe India is invite-only and doesn't support the needed marketplace flows for Indian platforms. Collect-then-payout risks unauthorised payment aggregation. Razorpay/Cashfree both provide split settlement; Razorpay documents transfer holds and reversals publicly.
- **Decision:** `PaymentGateway` port; Razorpay adapter (test mode) + FakeGateway; Cashfree as fallback adapter.
- **Reason:** Compliant funds flow, hold-until-delivered payouts, free test mode.
- **Revisit when:** international users/mentors (→ additional provider/entity), or Route terms/pricing change.

### ADR-006 — Double-booking prevention via exclusion constraint + transactional holds with TTL
- **Problem:** Concurrent bookings of the same slot; payment latency.
- **Options:** (a) app-level check-then-insert; (b) `SERIALIZABLE` transactions; (c) advisory locks only; (d) GiST exclusion constraint on active calendar blocks + hold state; (e) Redis locks.
- **Trade-offs:** (a) racy. (b) retries and complexity. (c) correct but easy to misuse. (e) extra infra with expiry pitfalls. (d) enforced by the DB regardless of code paths.
- **Decision:** (d), plus an advisory lock per mentor-local day for the max-per-day rule, lazy hold expiry inside the booking TX, and a late-payment re-acquire-or-refund path.
- **Reason:** Strongest guarantee with the least infrastructure.
- **Revisit when:** sharding the booking store (unlikely before very large scale).

### ADR-007 — Transactional outbox + tick endpoint for background work
- **Problem:** Emails, reminders, sweepers and webhooks processing without paid queues.
- **Options:** Host cron only; external queue (QStash/Inngest); outbox table + scheduler ping; in-process timers.
- **Trade-offs:** Outbox gives atomicity with state changes, but latency depends on tick frequency. External queues add a vendor. Timers are unreliable on serverless.
- **Decision:** Outbox table with `SKIP LOCKED` workers triggered by `pg_cron`+`pg_net` (and a GitHub Actions backup trigger). Correctness never depends on tick timing.
- **Reason:** Zero extra vendors; exactly-once-effect semantics with idempotent handlers.
- **Revisit when:** oldest-due job age > 5 min at peak (→ queue + worker).

### ADR-008 — Asynchronous booking-scoped messaging (no real-time chat in MVP)
- **Problem:** Communication needs vs complexity and moderation burden.
- **Options:** Real-time chat (WebSockets/Realtime service); async threads with email notifications; no messaging.
- **Trade-offs:** Real-time adds infra, presence, moderation at speed. No messaging hurts intake and logistics.
- **Decision:** Async threads tied to bookings + limited pre-booking inquiries; in-app notifications + email.
- **Reason:** Covers intake/logistics; simpler moderation; supports circumvention controls.
- **Revisit when:** measured demand (support tickets, NPS verbatims) for real-time.

### ADR-009 — Mentor-provided meeting links via a MeetingProvider port
- **Problem:** Video sessions without building video infrastructure.
- **Options:** Build WebRTC; embed Jitsi public (5-min embed limit, auth requirement); third-party SDK (paid per MAU); mentor-provided links; Google Meet API.
- **Trade-offs:** Links are simple but weak attendance evidence and a phishing risk. Meet API needs sensitive-scope verification.
- **Decision:** Manual links with strict host allowlist + platform join redirect (attendance signal); Google Meet/Zoom adapters in Beta.
- **Reason:** ₹0, no infrastructure, extensible.
- **Revisit when:** dispute rates show attendance evidence is insufficient.

### ADR-010 — Portable hosting; Vercel Hobby only for dev previews; public host chosen at Phase 16
- **Problem:** No ₹0 host is both commercial-use-compliant and ideal for full Next.js SSR.
- **Options:** Vercel Hobby (non-commercial); Netlify Free (commercial OK, hard cap); Cloudflare Workers Free (3 MiB limit); Render Free (sleeps); paid hosts.
- **Trade-offs:** See [04 §4.2](04-system-architecture.md#42-hosting-app-runtime).
- **Decision:** Keep the build vendor-neutral; defer the public host decision to measured bundle/traffic data; real money requires a paid commercial plan.
- **Reason:** Avoid premature lock-in and terms violations.
- **Revisit when:** Phase 16. (Originally "Phase 15" — renumbered 2026-09-26 when a new Phase 15, "Student/mentor application UI," was inserted ahead of the deploy phase; see docs/19's Phase overview note.)

### ADR-011 — 18+ only in MVP; configurable age policy
- **Problem:** Minors in 1:1 mentoring raise DPDP verifiable parental consent obligations and child-safety risks.
- **Options:** Allow all ages; allow 16+; 18+ with future guardian flow.
- **Trade-offs:** Excluding minors reduces the market (some undergrad applicants), but avoids unmanaged legal/safety risk.
- **Decision:** 18+ gate; `age_policy.min_age` per country; guardian-consent design in Future.
- **Reason:** Safety and compliance first.
- **Revisit when:** guardian flow designed + counsel sign-off.

### ADR-012 — Scoped evidence badges instead of generic "Verified" levels
- **Problem:** Verification labels that users over-trust, with misrepresentation risk.
- **Options:** Tiered "Verified" labels; scoped badges; no badges.
- **Decision:** Scoped, dated, method-specific badges; internal levels only for rules/filters.
- **Reason:** Accuracy, user understanding, legal risk reduction.
- **Revisit when:** third-party verification partners provide stronger identity/credential proofs.

### ADR-013 — Money as integer minor units + currency; double-entry ledger; snapshots
- **Problem:** Correct commission, refunds, reversals, taxes, multi-currency readiness.
- **Options:** Floats/decimals on booking rows; `numeric` columns; integer minor units + ledger.
- **Decision:** `bigint` minor units + ISO 4217; append-only double-entry ledger with DB-enforced balance; commission/policy snapshots per order item.
- **Reason:** Exactness, auditability, reconciliation.
- **Revisit when:** never for the core; the ledger may move to a dedicated service at scale.

### ADR-014 — Postgres full-text + trigram search with denormalised documents
- **Problem:** Multi-filter mentor discovery at ₹0.
- **Options:** Postgres FTS; Meilisearch/Typesense (hosting cost); Algolia (free tier limits, vendor).
- **Decision:** Postgres FTS + `pg_trgm` + GIN array filters on `mentor_search_documents`.
- **Reason:** No extra infra; document shape is reusable by an engine later.
- **Revisit when:** search p95 > 300 ms, or relevance needs (typo tolerance/facets) exceed Postgres.

### ADR-015 — REST (not GraphQL) with OpenAPI generated from zod
- **Problem:** API style for web now and mobile/partners later.
- **Decision:** Versioned REST; problem+json errors; cursor pagination; idempotency keys.
- **Reason:** Simpler authorization testing, caching, webhooks; see [06 §1](06-api-design.md#1-style-decision-rest-not-graphql).
- **Revisit when:** many heterogeneous clients need flexible aggregation.

### ADR-016 — Trust & safety policy engine as data, human-in-the-loop for severe actions
- **Problem:** Fair, adjustable enforcement (no-shows, misconduct) without hard-coded punishments.
- **Options:** Hard-coded thresholds; fully automated scoring; rules-as-data with human review.
- **Decision:** Trust events with points/decay/excuses; versioned rules proposing actions; auto-apply only low-severity, time-boxed restrictions; suspensions/bans need moderators (+ second reviewer for permanent bans); appeals.
- **Reason:** Fairness, configurability, alignment with GDPR Art. 22 principles and IT Rules grievance obligations.
- **Revisit when:** volume requires ML triage (assistive only).

### ADR-017 — Work-eligibility-aware mentor modes (volunteer vs paid)
- **Problem:** Current international students may be legally barred from paid self-employment.
- **Options:** Ignore (user responsibility only); ban current students; attestation + volunteer mode + evidence for paid.
- **Decision:** Attestation per country/status; volunteer default for restricted statuses; per-country rules configurable as counsel confirms.
- **Reason:** Protects mentors and the platform while keeping authentic supply.
- **Revisit when:** counsel confirms country-specific rules.

### ADR-018 — Data residency: primary DB and logs in India (Mumbai region)
- **Problem:** Latency for Indian users; CERT-In log requirements; DPDP posture.
- **Decision:** Supabase `ap-south-1`; host functions region closest to Mumbai where configurable; processors outside India documented.
- **Reason:** Performance + compliance posture.
- **Revisit when:** EU expansion (regional residency).

### ADR-019 — Mutations through REST route handlers; no Server Actions by default
- **Problem:** Next.js Server Actions are public endpoints that are easy to leave unauthorised, and they duplicate the API surface.
- **Decision:** All mutations go through `/api/v1` handlers with shared authz/idempotency/rate limits; Server Actions disallowed by lint unless allowlisted with a review.
- **Reason:** One hardened mutation path; consistent tests (BOLA matrix).
- **Revisit when:** framework conventions offer equivalent centralised guards.

### ADR-020 — Brand name isolated in configuration
- **Problem:** Temporary brand ("Aheadly") likely to change.
- **Decision:** Brand name, domain, colours, emails and legal entity name live in `src/config/brand.ts` and settings; no brand strings in schema, routes, cookie names (prefix from config) or code identifiers.
- **Reason:** Rename = config change + asset swap.
- **Revisit when:** final brand chosen.

### ADR-021 — Two-tier Content Security Policy (Phase 4)
- **Problem:** Nonce-based strict CSP requires dynamic rendering of every page, which defeats static/ISR SEO pages (docs/22 §10); a permissive CSP weakens XSS defence on authenticated pages.
- **Options:** (a) nonces everywhere (all pages dynamic); (b) experimental SRI hash-based CSP; (c) baseline CSP for all routes + strict nonce CSP only for authenticated dynamic areas.
- **Decision:** (c). All routes get a baseline policy from `next.config.ts` (`object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, `form-action 'self'`, self-only sources; scripts still allow `'unsafe-inline'`). Phase 5 adds a nonce-based policy via `proxy.ts` for `/dashboard` and `/admin`. SRI is re-evaluated once it is stable.
- **Reason:** Keeps SEO pages static while protecting the pages that handle personal data and money; public pages render no user-generated HTML in MVP.
- **Revisit when:** SRI leaves experimental status, or public pages start rendering user-generated content.

### ADR-022 — Toolchain baseline: Node 24 LTS, npm install-script denial, architecture tests over lint plugins (Phase 4)
- **Problem:** The machine had Node 23 (end-of-life, unsupported by Vitest 5); npm packages can run arbitrary install scripts; boundary rules need enforcement.
- **Decision:** Pin Node 24 LTS (`.nvmrc`, `engines`); keep npm 11's `allowScripts` denials for `esbuild` and `unrs-resolver` (both work without postinstall); enforce module boundaries, no Server Actions, public-env allowlist, raw-SQL timestamp handling and `sql.raw` confinement with fast Vitest architecture tests (`tests/architecture`) instead of adding `eslint-plugin-boundaries`/dependency-cruiser.
- **Reason:** Supported runtime, smaller supply-chain surface, fewer dependencies, rules that are easy to read and extend.
- **Revisit when:** The boundary rules become complex enough that a dedicated tool is clearer.

### ADR-023 — Auth core built directly on the platform pipeline instead of the Better Auth library (Phase 5, supersedes ADR-004)
- **Problem:** ADR-004 chose Better Auth for DB-backed sessions, Argon2id and TOTP. By Phase 5, the platform layer already had its own hashed-token sessions primitive (`crypto.ts`), audit log, rate limiter, idempotency layer and a single request pipeline (`defineRoute`) that gives every route CSRF checks, structured errors and audit hooks for free. Better Auth is designed to own its own route handler, cookie lifecycle and generated schema, which would mean either running two parallel request pipelines with different error/audit/CSRF behaviour, or fighting the library's assumptions to bolt it onto ours.
- **Options:** (a) mount Better Auth's catch-all handler alongside `defineRoute`; (b) call Better Auth's programmatic `auth.api.*` methods from inside our own routes; (c) implement the docs/07 spec directly against the platform's existing primitives.
- **Trade-offs:** (a) two error formats, two CSRF stories, two audit paths. (b) still adopts Better Auth's table shapes and session/cookie assumptions for no real savings, since every primitive it would provide (Argon2id, hashed sessions, TOTP, rate limiting) already existed in the platform layer from Phase 4. (c) more code written by us, and we own patching it if a flaw is found — the risk ADR-004 originally weighed against Better Auth, now taken on directly instead of inherited from a dependency.
- **Decision:** (c). `src/server/modules/auth` implements sign-up/verify/sign-in/MFA/password-reset/email-change/Google OAuth directly, using `@node-rs/argon2` for hashing and `jose` for Google's JWKS/id_token verification as the only new dependencies. Every behaviour in docs/07 (session lifetimes, step-up window, no-enumeration responses, pre-hijack defence, backup codes) is implemented and integration-tested as written; none of it changed to fit a library.
- **Reason:** One request pipeline, one error format, one audit trail, no second table-ownership model to reconcile with the `app` schema's UUIDv7/audit/settings conventions.
- **Revisit when:** the auth surface grows enough (passkeys, SSO, more OAuth providers) that hand-writing each flow costs more than adapting a library would.

### ADR-024 — HIBP breach checking and Turnstile CAPTCHA both fail open or are deferred, not blocking (Phase 5)
- **Problem:** docs/07 §4 asks for a Have I Been Pwned breach check and Turnstile-gated sign-in throttling. Both are third-party dependencies the app doesn't control.
- **Decision:** HIBP's k-anonymity range API needs no account or key, so it is implemented now (`infra/hibp-checker.ts`) and explicitly **fails open** (treats the password as clean) on any network error, per docs/07. Turnstile needs a registered site key tied to a real domain, which doesn't exist yet at $0 budget — it is deferred; the account- and IP-scoped rate limits already on `sign-up`/`sign-in`/`password-reset` stand in for it until a domain exists.
- **Reason:** Ship the check that's free and available now; don't block on infrastructure that can't exist yet, and don't let an optional check ever turn into an outage.
- **Revisit when:** a real domain exists to register Turnstile against.

### ADR-025 — Cross-module listing state: verification pushes a count, profiles owns the recompute (Phase 6)
- **Problem:** Whether a mentor is publicly listed depends on facts two different modules own: `profiles` owns the application status, `verification` owns credentials. `profiles` cannot import `verification` (verification already depends on profiles for affiliations — the reverse import would be circular), so `profiles` cannot count credentials itself when its own edits (bio, expertise, affiliations) need to recompute listing state.
- **Options:** (a) let `verification` import `profiles` in both directions (circular); (b) merge the two modules; (c) denormalise the credential count onto `mentor_profiles`, owned by `profiles`, updated only by `verification` calling an exported `profiles` function; (d) recompute listing from a live cross-module query at read time, outside either module (e.g. in route handlers).
- **Trade-offs:** (a) breaks the module-boundary architecture test and creates a real circular dependency, not just a lint violation. (b) throws away the credential/affiliation domain separation docs/05 and docs/10 both model as distinct. (d) works for a single profile page but doesn't help `profiles`' own mutations (editing a bio) know whether to keep a mentor listed, so an edit could silently un-list a verified mentor.
- **Decision:** (c). `mentor_profiles.active_credential_count` is written only through `profiles`' own `recomputeListingEligibility`, which the `verification` module calls (through `profiles`' public index) with a freshly counted value whenever a credential is issued or revoked. When `profiles` itself calls the same function after an unrelated edit, it omits the count and the last persisted value is reused — an edit can never accidentally guess wrong and un-list someone.
- **Reason:** Keeps the dependency graph a DAG (`verification → profiles`, never the reverse), keeps each module the sole writer of its own tables, and makes a real bug class (routine edits resetting verification state) structurally impossible rather than something a test has to catch.
- **Revisit when:** a third module needs to influence listing (e.g. trust & safety restrictions in Phase 10) — likely the same push-a-fact-in pattern, not a new exception.

### ADR-026 — University/company reference data is hand-curated, not a live ROR/GeoNames importer (Phase 6)
- **Problem:** docs/19's original Phase 6 scope called for "universities/cities import scripts (ROR + GeoNames + domains)". Building a real importer means alias reconciliation, dedup against admin edits (the seed is designed to never overwrite them, per docs/05 §8), and handling ROR's and GeoNames' data quirks — a distinct piece of engineering from the marketplace features this phase is about.
- **Decision:** Seed a hand-curated, factually-checked set (29 real universities and 9 real companies for India and Germany, with real institutional email domains, following the exact `slugify`/idempotent-insert pattern Phase 4 already established for countries and the category taxonomy) instead. Admins can extend it the same way Phase 4's taxonomy is extended — the schema (`ror_id`, `merged_into_id`, alias table) is already shaped for a future importer to fill in.
- **Reason:** Ships real, correct, verification-usable data now (the email-challenge flow needs accurate domains to mean anything) without deferring the entire phase behind an importer that's genuinely separate work.
- **Revisit when:** launch countries expand beyond India/Germany, or the curated list's maintenance burden exceeds writing the importer.

### ADR-027 — No-double-booking guarantee lives in a hand-written GiST exclusion constraint, not application code (Phase 7)
- **Problem:** docs/05 §4.1 specifies `calendar_blocks` must guarantee no two active blocks for the same mentor ever overlap, independent of isolation level or application bugs. Drizzle ORM (0.45) has no first-class `EXCLUDE USING gist` builder, so `drizzle-kit generate` cannot express this constraint from the table definition alone.
- **Options:** (a) enforce uniqueness only in application code (check-then-insert inside the booking transaction); (b) hand-write the whole `calendar_blocks` table as a custom migration, bypassing `drizzle-kit generate` for it entirely; (c) let `drizzle-kit generate` create the table and columns normally (including a `tstzrangeColumn` custom type for `during`), then add the `EXCLUDE` constraint and its supporting range-validity `CHECK` via one hand-written follow-up migration (`drizzle-kit generate --custom`), matching the precedent already set for triggers/functions in `0002_platform_triggers.sql`.
- **Trade-offs:** (a) is exactly the race docs/09 §6.1's worked example (two students booking the same slot simultaneously) is designed to defeat — a check-then-insert has a race window no amount of application care closes without the database's own conflict detection. (b) works but loses `drizzle-kit`'s drift detection for every other column on the table for no reason, since only the exclusion constraint itself is inexpressible.
- **Decision:** (c). `src/server/modules/booking/infra/tables.ts` defines `calendar_blocks` normally (columns, indexes, the `source_type` check); `drizzle/0007_booking_calendar_exclusion.sql` is hand-written and adds `calendar_blocks_no_overlap EXCLUDE USING gist (mentor_id WITH =, during WITH &&) WHERE (active)` plus the range-sanity checks from docs/05 §4.1. Verified directly against Postgres (not just unit-tested): a manual overlapping insert during development failed with SQLSTATE `23P01` exactly as documented, and four dedicated concurrency integration tests (docs/13 §6) exercise the real constraint under 10–20 parallel transactions.
- **Reason:** The guarantee has to be real at the database layer — that's the entire point of docs/09 §6's design — and hand-writing only the one inexpressible piece keeps everything else on the generated-migration path with drift detection intact.
- **Revisit when:** a future Drizzle ORM version adds native range/exclusion-constraint support, at which point `0007` could be folded back into a regenerated definition (no behaviour change, just less hand-written SQL to maintain).

### ADR-028 — A `raw` escape hatch on the route pipeline for redirects and non-JSON bodies (Phase 7)
- **Problem:** `defineRoute` (docs/04, ADR-019) always encoded a handler's return value as JSON. Two real Phase 7 routes can't use that: `GET /sessions/:id/join` must return a `302` redirect to the mentor's meeting URL (never exposed to the client as JSON, per docs/09 §12), and `GET /bookings/:id/calendar.ics` must return `text/calendar`, not `application/json`.
- **Options:** (a) write these two routes as plain Next.js route handlers outside `defineRoute`, re-implementing actor resolution, CSRF and logging by hand; (b) add an optional `raw?: Response` field to `RouteResult` that, when set, bypasses `jsonResponse()` entirely and is returned as-is (still going through the same actor/CSRF/idempotency/logging pipeline first).
- **Trade-offs:** (a) duplicates security-relevant pipeline logic in exactly the two places where getting it wrong matters most (a join redirect is an authorization-gated action; forgetting the actor check would leak meeting links). (b) is a small, generic addition every future non-JSON route benefits from, not a one-off hack for these two routes.
- **Decision:** (b). `RouteResult.raw` short-circuits just before JSON encoding in `route.ts`; everything before that point (params/body validation, actor resolution, CSRF, rate limiting, idempotency) runs exactly as for any other route, and the request is still logged.
- **Reason:** Keeps "every API route goes through one pipeline" true without forcing every response onto one wire format, and the two routes that need it are both auth-gated (join) or owner-gated (ICS), so they need the full pipeline more than most.
- **Revisit when:** a third distinct non-JSON case appears (e.g. streaming) — confirms this is a pattern worth a cleaner named helper rather than a single generic escape hatch.

### ADR-029 — `payments` never imports `booking`; the dependency runs one-directional via a denormalised `mentorUserId` and a booking-owned poll (Phase 8)
- **Problem:** `booking`'s own checkout step needs to call into `payments` (create an order/order item/payment intent as part of the booking transaction). Symmetrically, once a payment captures, *something* needs to confirm the corresponding booking — the obvious place is a `payments` webhook handler calling straight into `booking`. But `order_items` also naturally wants a foreign key back to the `booking_id` it belongs to, and `payments`' own transfer/ledger logic needs the mentor's user id off that order item. Letting both modules import each other's public index breaks the module-boundary architecture test and is a genuine circular ES module dependency, not just a style violation.
- **Options:** (a) let `payments`' webhook handler import `booking` and call a `confirmPaidBooking` function directly; (b) merge `booking` and `payments` into one module; (c) keep the dependency strictly one-directional (`booking → payments` only): `order_items` drops its FK to `bookings` (a plain unique `booking_id` column instead) and gains a denormalised `mentor_user_id` captured from the booking transaction's own input rather than looked up from `booking` at webhook time; `bookings` gains the FK to `order_items` instead (matching the direction code already needs to call in); `payments`' webhook/sweeper only ever update payment-side state, and `booking` owns a recurring poll (`syncPaidBookingsOnce`) that notices a payment succeeded and confirms its own booking.
- **Trade-offs:** (a) is the most direct wiring but creates the exact circular import the architecture test forbids, and mirrors the same instability ADR-025 already ruled out for `profiles`/`verification`. (b) throws away the bounded-context split docs/05 §2 and §3.4 both model as distinct, and would make every payments change touch booking's much larger transaction surface. (c) costs one poll interval of latency between a webhook arriving and the booking flipping to `confirmed` (mitigated by the 60-second `syncPaidBookings` recurring job, and by the webhook route itself remaining fast since it doesn't wait on `booking`'s transaction).
- **Decision:** (c) — the same push-a-fact-or-poll pattern ADR-025 established, applied at the schema level as well as the code level this time: the FK direction was flipped to match the required import direction, not left pointing the "natural" way and papered over with `@ts-ignore`-style import tricks.
- **Reason:** Keeps the module dependency graph a strict DAG (`booking → payments`, never the reverse) provably, at both the TypeScript and the SQL level, and keeps `payments` genuinely reusable by a future module (e.g. Phase 9's group sessions) without it ever needing to know `booking` exists.
- **Revisit when:** a second module needs the same "payment succeeded" fact — likely the same poll-or-push pattern, not a new exception; or if poll latency ever becomes a measured problem, at which point the webhook could instead enqueue a `booking`-owned outbox job by name (still no direct import) rather than shortening the poll interval.

### ADR-030 — Only a `FakeGateway` this phase; a real Razorpay adapter is deferred (Phase 8)
- **Problem:** docs/19's original Phase 8 scope included a Razorpay test-mode adapter, but building one needs a registered Razorpay account and test API keys — a founder action item that was never actioned (no business entity or domain to register against yet, consistent with this project's $0-budget, pre-incorporation stage).
- **Options:** (a) block the whole phase on getting test keys first; (b) build the full `PaymentGateway` port and every consumer (checkout, webhooks, refunds, transfers, the sweeper) against it, backed only by `FakeGateway` — an implementation of the same port against a separate `fake_psp` Postgres schema standing in for "the outside world" — and defer the real adapter.
- **Trade-offs:** (a) stalls all of Phase 8's actual engineering (state machines, ledger, commission engine, refund/transfer logic) on an external dependency outside this project's control. (b) means the webhook signature verification, retry/idempotency and failure-mode code paths are only proven against a fake provider's behaviour, not Razorpay's real quirks (its actual webhook payload shapes, its actual failure modes) — a real risk this ADR names rather than hides.
- **Decision:** (b). Every consumer depends only on the `PaymentGateway` interface (`application/ports.ts`); `FakeGateway` is a complete implementation, including genuinely HMAC-signed webhooks dispatched to the real `/api/webhooks/fake` route (not a shortcut that pokes our own rows directly) so the signature-verification and dedupe code is exercised for real. The boot-time guard refusing `rzp_live_*` keys outside `NODE_ENV=production && PAYMENTS_MODE=live` (docs/08 §13 point 9) is built now specifically so a real adapter is a drop-in later with no call-site changes.
- **Reason:** Ships the engineering that's actually testable and correct-by-construction now (ledger balance, commission math, state machines, refund clawback) without deferring the entire phase behind an account signup this project can't yet complete.
- **Revisit when:** a Razorpay test account exists (docs/19's founder action item, still open) — the exit criterion "Razorpay test-mode happy path verified manually" is explicitly carried forward, not silently dropped.

### ADR-031 — Ledger-posting functions take a caller-supplied `Executor`, never open their own transaction (Phase 8)
- **Problem:** `ledger_journals`/`ledger_lines` are protected by a `DEFERRABLE INITIALLY DEFERRED` constraint trigger (`app.assert_journal_balanced()`) so a journal's debits and credits are only checked once the *whole* transaction commits, not after each individual insert — otherwise a multi-line journal would fail the balance check the instant its first line was written, before the rest existed. Postgres only defers a trigger to the end of an *explicit* transaction; a multi-statement operation run against a bare (non-transactional) `Database` handle autocommits each statement individually, which fires the balance check prematurely on partial data and — discovered via a scratch smoke test during this phase — also leaves a permanently unusable idempotency-keyed journal header row behind (the header insert had already autocommitted before the failing line insert rolled back only itself).
- **Options:** (a) have every ledger-posting function (`refundOrderItem`, `adminReleaseTransfer`, etc.) open its own `db.transaction(...)` internally; (b) have them accept a generic `Executor` (satisfied by both a plain `Database` and an open transaction) and never open a transaction themselves, requiring every call site to wrap the call in `db.transaction()` explicitly.
- **Trade-offs:** (a) is simpler at each individual call site but breaks the moment a ledger post needs to happen atomically alongside something else — exactly `booking`'s cancellation flow, which must transition the booking status *and* post the refund journal in one commit-or-nothing unit (docs/09's own atomicity requirement for cancellation). A function that always opens its own transaction can't be composed into a larger one (Postgres has no true nested transactions without savepoints this codebase doesn't use). (b) pushes the transaction-boundary decision to whoever actually knows the right boundary — the call site — matching the pattern already established for `booking`/`profiles`/`verification` repository functions throughout this codebase.
- **Decision:** (b). `refundOrderItem` takes an `Executor` and never opens its own transaction; `booking`'s cancellation flow calls it with its own already-open `tx`, while standalone callers (the admin refund route, the orphan-booking sync job) explicitly wrap the call in `db.transaction(...)` themselves. Every such call site was audited after the smoke-test discovery to confirm none call a ledger-posting function on a bare `Database`.
- **Reason:** "Explicit over implicit" for transaction boundaries was already this codebase's standing convention before Phase 8; the alternative would have created a function that behaves correctly in isolation but corrupts state the moment it's composed into a larger operation — exactly the kind of bug that doesn't show up until the second caller.
- **Revisit when:** never expected to change — this is the same discipline the rest of the codebase already follows, made load-bearing here because the deferred-trigger's silent-until-composed failure mode makes getting it wrong unusually expensive.

### ADR-032 — Group sessions and free events extend `booking`; no separate `events` module (Phase 9)
- **Problem:** docs/04 §5's code-organisation diagram lists a standalone `events/` folder alongside `payments/`, but docs/05 §2's bounded-context table puts `waitlist_entries`/`event_details`/`event_invites` inside the single "Scheduling & booking" context next to `sessions`/`bookings` — the two planning docs disagree about whether Phase 9 is a new module or an extension of the existing one.
- **Options:** (a) a new `events` module, following docs/04's diagram; (b) extend `booking`, following docs/05's bounded-context table and schema ownership.
- **Trade-offs:** (a) would need its own public index, its own architecture-boundary-test entry, and — critically — either a new cross-module dependency on `booking`'s `sessions`/`bookings` tables (which it doesn't own) or a duplicated session/booking concept for group and event seats specifically. Group seats and 1:1 bookings already share one `bookings` table with one state machine, one cancellation flow and one attendance finaliser (docs/09 §7, §11); splitting event registrations out into a second module would mean either reimplementing all of that or importing across a boundary this codebase has otherwise kept strict. (b) costs nothing new: `sessions.kind` (`one_on_one`/`group`/`event`) and every capacity/pricing column already existed on the `sessions` table since Phase 7, reserved for exactly this.
- **Decision:** (b). Three new tables (`waitlist_entries`, `event_details`, `event_invites`) and this phase's application code all live in `src/server/modules/booking`; the `events/` entry in docs/04's diagram is treated as a documentation artifact from before docs/05's bounded-context table was finalised, not a second module to build. `payments` (ADR-029's DAG) is unaffected either way.
- **Reason:** One `sessions`/`bookings` pair, one state machine, one cancellation and attendance pipeline — group seats and event registrations are variations in *how a seat gets granted and priced*, not a different kind of thing needing their own storage or module boundary.
- **Revisit when:** group/event scope grows enough (e.g. Phase 20's paid-events/workshops future line) that `booking` itself becomes unwieldy — at that point splitting scheduling from marketplace-seat-selling might earn its own ADR, but that's a size problem to solve when it arrives, not one this phase has.

### ADR-033 — A waitlist offer is a soft promise, not a hard hold; capacity is re-verified at claim time (Phase 9)
- **Problem:** docs/09 §8 says a freed paid group seat gets offered to the next waitlisted student with a claim window; docs/09 §9 says a freed free-event seat auto-promotes directly with no claim step. Neither section specifies what happens if two things want the same seat at once — a claim racing a concurrent direct booking, or (in principle) two offers somehow both pointing at one physical seat — and docs/13 §6 explicitly names "two users claim one freed seat, one succeeds" as a concurrency scenario this phase must cover.
- **Options:** (a) treat an "offered" waitlist entry as a hard reservation — increment some notion of reserved capacity the moment an offer is created, so the seat can't be claimed by, or booked over by, anyone else; (b) treat an offer as advisory only — `waitlist_entries.status = 'offered'` records *who's turn it is*, but the actual capacity check (`live seats < capacity`, under the session's row lock) re-runs at claim time exactly like a fresh direct booking would.
- **Trade-offs:** (a) needs a second capacity accounting scheme alongside the `bookings` table's own live-seat count (a reserved-but-not-booked seat isn't a `bookings` row yet), which either means a new column/table to track reservations or subtracting outstanding offers from capacity everywhere seats are counted — real complexity for a promise that, per docs/09 §8's own 2-hour window, is expected to often lapse anyway. (b) is a few lines: the claim route runs inside the same `findSessionForUpdate` lock `bookSeat` uses and just checks capacity again; if it's gone (raced away by someone else), the offer is marked `expired` and immediately cascades to whoever's next, rather than leaving a stranded offer.
- **Decision:** (b). `claimWaitlistOffer` re-verifies live-seat count under the session lock before granting the seat; losing that race is a clean `SLOT_UNAVAILABLE`, not a corrupted double-grant, and the loser's offer cascades onward automatically. The same lock is what makes "50 parallel seat requests for capacity 10 → exactly 10" and "claim vs. direct booking, exactly one wins" both hold structurally, not by convention.
- **Reason:** A single source of truth for "how many seats are taken" (the `bookings` table, under one lock) is safer than two schemes that have to agree with each other, and an offer being "just a notification with priority," not a reservation, matches what docs/09 §8 already implies by giving it an expiry at all.
- **Revisit when:** a real hard-hold-on-offer becomes a product requirement (e.g. a premium waitlist tier) — at that point it's a genuinely new reservation concept worth its own table, not a retrofit of this one.

### ADR-034 — Group-seat cancellation reuses the 1:1 cancellation policy; the calendar-block release and session-cancel become session-kind-aware (Phase 9)
- **Problem:** Two of docs/09's own sections disagree about a group seat's own cancellation refund policy: §8's local table sketches a binary "full refund before a 24h deadline, none after"; docs/17 §5's business-rules header instead states the tiered `cancellation.student.*` window rules (24h full / 6h partial / late) apply to "1:1 **and group seats**," with only the *min-participants-unmet* case getting its own distinct 100% override. Separately, `cancelBooking` (built Phase 7, 1:1-only) unconditionally released the session's calendar block and marked the whole session `cancelled` on any single booking's cancellation — correct when a booking *is* the session, but would silently cancel an entire live group session the first time any one of its students cancelled their own seat.
- **Options for the refund policy:** (a) build docs/09 §8's separate binary policy as its own thing; (b) treat docs/17's explicit, more recently-written statement as authoritative and reuse the existing tiered cancellation flow unchanged for group seats. **Options for the calendar-block/session-status bug:** (c) leave `cancelBooking` as-is and give group/event seats their own separate cancellation function, duplicating the claim/refund/notify logic that isn't kind-specific; (d) make `cancelBooking` itself kind-aware — only release the calendar block and cancel the session when `sessionKind === "one_on_one"`; trigger the waitlist cascade instead for group/event.
- **Trade-offs:** (a) is more code for a policy that's actually redundant with what already exists, and directly contradicts docs/17's own words. (c) duplicates the entire claim/audit/refund/notify body of `cancelBooking` for a difference that's really just "what happens to the calendar block," not a different cancellation policy. (d) is a small, targeted fix to the one function, matching how this codebase has resolved every other cross-doc/legacy-gap tension so far (Phase 8's confirm-vs-cancel fix, ADR-025's push-a-fact pattern) — fix the shared function to be correct for every caller rather than fork it.
- **Decision:** (b) + (d). `loadParticipant` now also returns the session's `kind`; `cancelBooking` only releases the calendar block and marks the session cancelled for `one_on_one`, and for `group`/`event` instead calls `offerOrPromoteNextInLine` — the seat that just freed up gets offered or auto-promoted per ADR-033, and every other confirmed seat in the session is untouched. Group/event's own *whole-session* cancellation (the mentor pulling the plug entirely) is a genuinely separate action (`cancelGroupSession`/`cancelEvent`), not something `cancelBooking` should ever do as a side effect of one seat leaving.
- **Reason:** One cancellation policy, one enforcement function, correct for every session kind it's ever called against — the alternative (a parallel policy plus a parallel function) would have shipped two things to keep in sync for no benefit docs/17 doesn't already provide for free.
- **Revisit when:** a real product reason emerges for group seats to have their own cancellation *refund* policy distinct from 1:1 (docs/17 §5's header would need to change first) — the kind-aware calendar-block/session-status fix itself should never need revisiting; it was a latent correctness gap, not a policy choice.

### ADR-035 — `trust` sits at the top of the module DAG; `user_blocks`/`user_restrictions` live in `auth`, and `booking` pushes audit-log signals rather than importing `trust` (Phase 10)
- **Problem:** `trust` (reports, moderation, policy engine, disputes, reviews) needs to read and write things every other module already owns — a mentor's listing (`profiles`), a booking's status and a refund (`booking`, `payments`), and it needs to *block new bookings/logins* the instant a restriction is applied. The obvious place to check "is this capability restricted" is inside `authorize()`, which every module's routes already call — but `authorize()` and the session actor live in `auth`, and `booking` already depends on `auth` (not the reverse). If `trust` owned `user_restrictions` itself, either `auth`'s actor resolver would need to import `trust` (a new module reaching down into a module that would sit above it — a cycle), or `booking`/`payments`/`profiles` would each need a direct `trust` dependency just to run a restriction check, multiplying the surface for a cycle to form later.
- **Options:** (a) a new `user_blocks`/`user_restrictions` table pair owned by `trust`, with `auth`'s `resolveSessionActor` importing `trust` to hydrate `actor.restrictions`; (b) own both tables in `auth` instead — `trust` calls `auth`'s public functions (`insertRestriction`, `hasActiveRestriction`, …) to create and check them, the same way every other module already reaches into `auth` for `findUserById`/`authorize`; (c) put `trust` *below* `auth` in the DAG and have `auth` import `trust` for restrictions only, keeping blocks/everything else in `trust`.
- **Trade-offs:** (a) is the most semantically "correct" ownership (trust concepts living in the trust module) but directly creates the `auth ↔ trust` cycle the architecture-boundary test forbids, since `auth` is foundational and every other module (including `trust`) already depends on it. (c) avoids the cycle but splits one cohesive concept (moderation restrictions) across two modules for no real reason, and still leaves `trust` needing to trigger things in `booking`/`profiles`/`payments`, which are *below* `auth` in the graph — `trust` would end up needing to sit both above and below `auth` simultaneously, which isn't a DAG. (b) costs nothing architecturally: `auth` already has a `Restriction`/`Capability` type and an actor-resolver comment anticipating exactly this ("one deliberate place the platform pipeline reaches into a specific module"); `trust` becomes the *top* of the graph (imports `auth`, `booking`, `payments`, `profiles`, never imported back by any of them), matching the same shape `payments`/`profiles` already have relative to what they depend on.
- **Decision:** (b), plus the same one-directional "push a fact, poll or react on the other side" discipline ADR-029 established for `payments ↔ booking`: `booking`'s attendance finalizer and cancellation flow write plain `writeAudit(...)` signal rows (`booking.mentor_no_show_signal`, `booking.mentor_late_cancel_24h_signal`, etc.) — `booking` never imports `trust`. `trust`'s own audit-log ingestion poller (`ingestPendingAuditSignals`, watermarked by `trust_ingestion_watermark`) is the only thing that converts those signals into real `trust_events` rows, immediately re-evaluating the policy engine. Trust events are sourced by `sourceType: "booking", sourceId: <bookingId>` rather than the ingesting audit-log row's own id, specifically so a later dispute resolved in the mentor's favour can excuse exactly the event(s) tied to *that booking* (`excuseTrustEventsFromSource`) without needing any reference back to the audit log.
- **Reason:** Keeps the module graph acyclic at both the TypeScript and conceptual level: `trust` can freely read and act on every other module's public surface (it's meant to be the platform's final authority over enforcement), while nothing below it ever needs to know it exists, exactly mirroring how `payments`/`profiles` stay ignorant of `trust` today and how `booking` already stayed ignorant of `payments`' internals under ADR-029.
- **Revisit when:** a module *above* `trust` is ever needed (none is anticipated — `trust` is deliberately the capstone of the graph); or if audit-log poll latency (currently a 60s recurring job) ever becomes a measured problem for how quickly a restriction should take effect after the triggering event, at which point the same enqueue-a-named-job escape hatch ADR-029 named would apply here too.

### ADR-036 — The policy evaluator returns the specific trust-event ids it matched on, not just a boolean; `moderation_actions.restriction_scope` carries them forward for precise appeal excusal (Phase 10)
- **Problem:** docs/10 §7.4 says an overturned appeal "excuses related trust events" — but a triggered rule's `sum_points_gte`/`count_type_gte` condition is evaluated against a whole window of a subject's events, several of which may also have contributed to (or will later contribute to) a *different* rule's trigger. Naively excusing "every trust event for this subject sourced from roughly the same time" on overturn risks silently wiping out evidence a separate, still-valid action also depended on; naively excusing nothing at all leaves the exact events that triggered a now-reversed action still on the books to (wrongly) re-trigger the same or a harsher rule on the next policy-engine run.
- **Options:** (a) on overturn, excuse every non-excused event for the subject within the rule's own window — simple, but over-broad (as above); (b) don't excuse anything automatically; require a human to manually excuse each event via the admin trust-event tools — correct but adds a manual step to every single overturned appeal, and is easy to forget; (c) have the pure evaluator itself report exactly which live event ids fed the condition that matched (`contributingEventIds`, added to `PolicyEvaluationResult`), thread that list through `applyModerationAction` into `moderation_actions.restriction_scope`, and have an overturned appeal (or a direct staff revoke) excuse precisely those ids.
- **Trade-offs:** (a) is a few lines but is exactly the kind of imprecision docs/10 principle 2 ("evidence-based") argues against — it would let one overturned warning silently launder unrelated events. (b) is precise but not "the platform doing the obviously-correct thing automatically," which is what appeals are supposed to deliver per docs/10 §7.4. (c) needed a small, deliberate domain-type change (`TrustEventFact` gained an `id` field it didn't need before, since the evaluator previously only ever summed/counted points, never needed to name individual events) but costs nothing at the call sites: `policy-engine.ts` already had the live event rows in hand when it called `evaluatePolicyRule`, it just wasn't passing their ids through, and manually-decided actions simply carry an empty list (nothing to excuse if staff never named a trigger).
- **Decision:** (c). `evaluatePolicyRule`'s triggered result now includes `contributingEventIds: string[]` — every live event id for `sum_points_gte`, only the matching-type ids for `count_type_gte`, and empty for `rate_gte` (which has no discrete backing events at all, being derived from booking session counts). `enforcement.ts`'s shared `reverseModerationAction` (used by both an overturned appeal and a direct staff revoke) reads that list back off the action row and excuses exactly those events.
- **Reason:** Appeals should be able to precisely undo the *specific facts* that triggered an action without collateral damage to unrelated evidence, and without requiring a human to reconstruct "which events actually mattered" after the fact from a raw event list.
- **Revisit when:** the evaluator gains a condition kind that isn't a simple sum/count over discrete events (e.g. `rate_gte` already has no ids to give); that new condition kind's contract for `contributingEventIds` should be decided the same way `rate_gte`'s was — explicitly, not left to fall through to an empty list by accident.

### ADR-037 — Dispute resolution computes its own refund percentage and calls `payments.refundOrderItem` directly; no new booking state-machine transitions (Phase 10)
- **Problem:** docs/10 §8 describes dispute outcomes as "full refund / partial refund (split) / no refund," including an explicit 50/50 balanced-split example — but booking's own state machine (built Phase 7/9) only has two exits from `disputed`: `dispute_resolved_for_mentor → completed` and `dispute_resolved_for_student → resolved_refunded` (the latter carrying a `refund_full` intent). Taken literally, a *partial* refund doesn't fit either named transition.
- **Options:** (a) add new booking statuses/transitions for `resolved_partial_refund` and thread an arbitrary refund percentage through the state-machine's `TransitionIntent` type; (b) treat `dispute_resolved_for_student`'s existing transition and `refund_full` intent as *nominal* labels rather than literally-enforced ones — nothing in the codebase actually reads `intent.type === "refund_full"` and asserts the refund is 100% — and have `trust` compute the actual refund amount itself (via a new pure `domain/dispute-math.ts`: `resolveRefundPct`/`refundMinorFor`/`evidenceFavoredResolution`), then call `booking.transitionBookingStatus` directly with whichever of the two existing target statuses fits (`completed` if nothing is refunded, `resolved_refunded` for any refund > 0) and separately call `payments.refundOrderItem` with that computed amount.
- **Trade-offs:** (a) is the "textbook" fix but touches a state machine three prior phases have already built and tested around, for a distinction (partial vs. full refund) that the booking status itself never actually needed to know — from booking's point of view, "some money went back to the student" is one outcome, and the *how much* already lives entirely in `payments`' own `refunds` table. (b) costs nothing in `booking` at all and keeps the money-percentage decision where the dispute logic actually lives, but does mean `trust` bypasses booking's own (unexported) `transition()`/`canTransition()` validation table, since that table isn't part of booking's public surface — `disputes.ts` instead hardcodes its own small, explicitly-commented allow-list of the exact statuses a dispute can be opened from, mirroring the same two transition rules by name.
- **Decision:** (b). `resolveDispute` computes `refundPct` via `dispute-math.ts`, calls `transitionBookingStatus` straight to `completed`/`resolved_refunded`, and — for any refund > 0 — calls `payments.refundOrderItem` with the computed minor-unit amount, inside one transaction. A dispute that originated from a contested no-show and resolves *for* the mentor (no refund) also excuses the trust event that no-show produced (`excuseTrustEventsFromSource`, keyed by booking id per ADR-035); resolving *against* the mentor doesn't fabricate a second trust event, since the ingestion poller already recorded the matching one from the original finalizer signal, and `recordTrustEvent`'s own idempotency makes a duplicate call a no-op.
- **Reason:** No existing code anywhere actually depended on `refund_full`'s literal 100% meaning, so reusing the transition unchanged for "any refund" costs nothing and keeps three phases of prior, already-tested state-machine work untouched — exactly the same reasoning ADR-034 applied to reusing the cancellation policy for group seats rather than forking it.
- **Revisit when:** booking ever needs to *know* whether its own refund was full or partial for some reason other than the amount already recorded in `payments` (e.g. a future analytics field on `bookings` itself) — at that point the state machine's `refund_full` intent should either be split or dropped in favour of reading the actual amount from `payments`, not silently kept as a misleading label.

### ADR-038 — Off-platform-circumvention detectors are built as reusable pure functions now; only reviews wire them up this phase, not messaging (Phase 10)
- **Problem:** docs/10 §9 (contact-info/payment-solicitation detection) and §3.2 (claim-phrase detection) are both written assuming a messaging module exists to run them against — but Phase 7's booking scope explicitly deferred messaging/conversations, and no later phase (8 or 9) ever picked it back up (confirmed by searching the codebase and docs/19's own phase list: there is no messaging module and no scheduled "Phase 7b"). Phase 10 is also the phase docs/19 assigns the detectors' actual *build*, not just their eventual wiring.
- **Options:** (a) block the detector work on first building a minimal messaging module, since that's the primary surface docs/10 §9 describes; (b) build the detectors as pure, input-agnostic domain functions (`detectContactInfo`, `detectClaimPhrases`, `containsProfanity`, `shouldHoldForModeration`) with no dependency on any particular caller, and wire them into whichever text surfaces already exist — this phase, review bodies and review responses (docs/10 §10's own publication-check table already lists "contact-info"/"claim phrases" as review-hold reasons, independent of messaging).
- **Trade-offs:** (a) stalls the entire trust-event catalog's off-platform-solicitation entries and this phase's detector unit-test requirement (docs/13 §3) behind a whole new module that's its own multi-week undertaking, matching neither this phase's scope nor docs/19's phase boundaries. (b) means `off_platform_solicitation_first`/`off_platform_solicitation_repeat` (the two catalog entries whose "created when" column literally says "moderator-confirmed flag" from messaging) have no automatic producer this phase — the same documented-gap treatment already given to `hold_abuse`, `mentor_late_arrival_reported`, `chargeback_lost_friendly_fraud` and `verification_fraud`, each of which also names a producer this phase doesn't build.
- **Decision:** (b). The detectors live in `trust/domain/detectors.ts` as pure functions taking raw text and returning typed hits, with no knowledge of where the text came from — deliberately reusable later by a messaging module, profile/service text (docs/10 §3.2), or booking intake answers without any of them becoming a new dependency of `trust`. This phase's only wired-up caller is `reviews.ts`'s publication-check pipeline.
- **Reason:** Building the reusable primitive now (and unit-testing it thoroughly, including the ReDoS-safety work this phase's own detector regexes needed) means messaging, whenever it's built, is a wiring exercise against an already-correct detector rather than a phase that has to build and test detection logic itself.
- **Revisit when:** a messaging module is scheduled — at that point it calls `detectContactInfo`/`hasPaymentSolicitation` directly per docs/10 §9's nudge/block rules, and the two solicitation trust-event types gain their first real producer.

### ADR-039 — The public site and `/admin/*` get separate root-adjacent layouts via a route group; a new `requireStaffPage` mirrors `defineRoute`'s staff gate for Server Components (Phase 11)
- **Problem:** every page built through Phase 10 (`/`, `/mentors`, `/events`) is public, and the true root layout (`src/app/layout.tsx`) rendered the public `SiteHeader`/`SiteFooter` directly around `{children}` — so any new page nested under it, including a staff console, would inherit the marketing site's nav and footer. Separately, no Server Component anywhere had ever needed to know who's signed in: `resolveActor` is called from exactly one place (`defineRoute`, inside the API pipeline), and there was no cookie-reading, actor-resolving, role-checking helper a *page* could call.
- **Options for the layout split:** (a) keep one root layout and have `admin/layout.tsx` fight the inherited header/footer with CSS overrides or conditional rendering keyed off the pathname; (b) move `SiteHeader`/`SiteFooter` out of the root layout into a `(public)` route group wrapping the existing public pages, leaving the root layout as a bare document shell, and give `/admin/*` its own, unrelated layout. **Options for the auth helper:** (c) have every admin page manually re-derive `resolveActor`'s cookie-parsing logic inline; (d) build one reusable `requireStaffPage(roles, returnTo)` that reconstructs a minimal `Request` from `next/headers`' cookie jar and calls the *existing* `resolveActor`, then runs the same `authorize(actor, requireStaff(roles), ...)` policy every API route already uses, translating each denial into the right redirect or a real 404.
- **Trade-offs:** (a) is fragile — CSS overrides fighting inherited chrome are exactly the kind of thing that silently breaks the next time either side changes, and Next.js route groups exist precisely to avoid this. (b) is a clean, mechanical move (route groups are transparent to URLs — `(public)/mentors/page.tsx` still serves `/mentors`) that costs one extra layout file. (c) would duplicate and likely drift from the API pipeline's own cookie-parsing/token-validation logic across 20+ pages. (d) reuses `resolveActor` byte-for-byte (no parallel identity-resolution implementation to keep in sync) and reuses the *exact* `requireStaff`/`requireStaffWithMfa` policy functions already proven correct by every existing admin route's tests, so a page and its matching API route can never disagree about who's allowed in.
- **Decision:** (b) + (d). The root layout is now `<html>`/`<body>` plus fonts and nothing else; `(public)/layout.tsx` carries `SkipLink`/`SiteHeader`/`SiteFooter`; `admin/layout.tsx` is a bare styling wrapper with no auth check (needed so `/admin/login` and `/admin/mfa` can render without it); the actual gate lives one level deeper in `admin/(dashboard)/layout.tsx`, which calls `requireStaffPage` with the broadest staff role set and each individual page additionally narrows to its own specific role requirement, mirroring how each admin *API route* already scopes roles per action rather than at one shared checkpoint. `requireStaffPage`'s three outcomes: not signed in → redirect to `/admin/login?returnTo=...`; signed in but not staff → `notFound()` (never a 403 — matching `requireStaffWithMfa`'s own `NOT_FOUND` denial, so a non-staff user can't even confirm the admin surface exists); staff but this session's MFA isn't verified → redirect to `/admin/mfa?returnTo=...`.
- **Reason:** One identity-resolution implementation and one authorization-policy set, shared by both the API and the page layer, is the only way a page's "can view" and its matching route's "can act" guarantees can't drift apart — a real risk for a staff console where the page and the route are built as separate files.
- **Revisit when:** a genuinely page-specific auth requirement emerges that `requireStaff`'s role-list shape can't express (none anticipated — every admin page's access rule so far is "one of these named roles, MFA-verified").

### ADR-040 — A new `verifyMfaStepUp` elevates an already-signed-in session's MFA state directly, instead of routing every step-up through a full re-sign-in (Phase 11)
- **Problem:** docs/07 §3.6 makes MFA mandatory for every staff request, enforced by `requireStaffWithMfa` checking `actor.mfaVerified` — a flag that lives on the *session* row (`auth_sessions.mfa_verified`), not the user. Building the staff sign-in flow surfaced that only one function in the whole codebase ever sets that flag to `true`: `completeMfaSignIn`, which exclusively handles the *pending-token* path from a brand-new sign-in attempt. A staff member's ordinary first-time path — sign in with just a password (no MFA enrolled yet, so `signIn()` returns `signed_in` directly, not `mfa_required`), then enroll MFA — had no function anywhere that could mark *that already-existing session* as MFA-verified once enrollment finished. The only way to reach an `mfaVerified: true` session was to sign out and back in through the full pending-token flow.
- **Options:** (a) after enrolling, force a full sign-out/sign-in cycle (discard the current session, issue a fresh one via the existing `completeMfaSignIn`-adjacent path) so every session that ever becomes MFA-verified does so through the one already-tested code path; (b) add a new, narrower function (`verifyMfaStepUp`) that checks a submitted code against an already-enrolled secret and calls the existing (but previously unused outside sign-in) `markSessionMfaVerified` directly on the *current* session, exposed via a new `POST /api/v1/auth/mfa/step-up` route; also wire `mfa/enroll/confirm` to call the same session-marking step immediately after a successful enrollment, since confirming already proves live code possession.
- **Trade-offs:** (a) reuses proven code but is a strictly worse user experience for zero security benefit — the session is already known-good (it passed primary auth), so discarding and reissuing it just to flip one boolean adds a redundant round trip and a confusing "you got logged out" moment right after finishing setup. (b) needed a genuinely new function, but it's a small, obvious one (the same TOTP/backup-code verification `completeMfaSignIn` already does, factored to act on an existing session instead of issuing a new one) and closes a real gap that would otherwise have blocked *every* staff member from ever reaching a usable admin session on their first sign-in.
- **Decision:** (b). `verifyMfaStepUp` is deliberately gated by `requireUser` only, not `requireRecentUserAuth` — requiring recent *password* re-authentication on top of a valid MFA code would be circular for exactly the case this exists to solve (a session that's stale on the recent-auth clock but still cryptographically proven via TOTP). `mfa/enroll/confirm`'s route calls `markSessionMfaVerified` directly after `confirmMfaEnrollment` succeeds, rather than making the client immediately re-submit the same code to the new step-up endpoint (which would also fail — `verifyTotp`'s replay protection advances the accepted counter on first use, so the same code can't be verified twice).
- **Reason:** MFA step-up should prove "I have the second factor right now," which a valid TOTP/backup code already does on its own — it shouldn't implicitly also require restarting the primary-auth session just to record that proof against the session that's already running.
- **Revisit when:** never expected to change on its own; if passkeys (docs/07 §3.6, Beta) are ever built, they'd likely want the same "step up the current session directly" treatment rather than reusing the sign-in-token path either.

### ADR-041 — The admin console is built with a plain server-rendered `Table` and a handful of owned components, not a data-grid or additional Radix primitives (Phase 11)
- **Problem:** docs/22 §6.4's component inventory names a "Table (admin; sortable, filterable, paginated)" alongside Dialog/Sheet/Tabs/Toast/Combobox and more, all described as "Radix primitives + owned components" — but confirmed by inspecting `src/ui/` and `package.json` before starting this phase, only seven small owned components existed (`Button`, `Card`, `Badge`, `EmptyState`/`ErrorState`, `Skeleton`, `Container`, `SiteHeader`/`SiteFooter`) and exactly one Radix package (`@radix-ui/react-slot`, used solely for `Button`'s `asChild`) — none of the richer primitives the docs describe were ever built, and no table/data-grid or charting library was ever installed.
- **Options:** (a) pull in `@tanstack/react-table` (or similar) for sortable/filterable/paginated tables, plus `@radix-ui/react-dialog`/`-tabs`/`-toast` to build out the fuller component set docs/22 describes, matching the original design-system intent; (b) build the admin console's ~20 pages against the existing minimal component style — a plain server-rendered HTML `Table`, `Field`/`Input`/`Select`/`Textarea` for forms, a small `ActionButton`/`adminFetch` pair for mutations — adding only what's strictly needed, with native `window.confirm`/`window.prompt` standing in for a confirm dialog.
- **Trade-offs:** (a) matches the original design-system vision and would give richer client-side interaction (in-browser sorting/filtering without a full page reload), but adds real dependency weight and complexity to a project that has otherwise stayed deliberately dependency-lean at every prior phase (`FakeGateway` over a real provider adapter, hand-rolled settings/feature-flag infrastructure over a config-management SaaS, no ORM beyond Drizzle). It would also mean most admin pages become Client Components fetching their own data, a real departure from the Server-Component-first pattern every existing page (`mentors/page.tsx`, `events/page.tsx`) already uses. (b) keeps every list page a plain Server Component querying the database directly (the same pattern `mentors/page.tsx` established in Phase 6) with sorting/filtering left to server-side query parameters this phase didn't build UI controls for yet, and correctly renders every admin table this phase needed without a single new runtime dependency.
- **Decision:** (b). `src/ui/table.tsx` is four plain HTML-element wrappers with Tailwind classes; `src/ui/action-button.tsx` and `src/ui/admin-fetch.ts` are the only new *interactive* primitives, reused across all ~15 mutation forms this phase built. No new npm dependency was added for UI at all this phase.
- **Reason:** An admin console for a pre-launch, ₹0-budget marketplace doesn't yet have the traffic or table sizes (tens to low hundreds of rows) that would make client-side sorting/filtering/virtualisation worth a new dependency and a Server-Component-to-Client-Component architecture shift — server-side `?status=` query-param filtering (already built on several list routes) covers the actual current need.
- **Revisit when:** an admin table's row count or interaction needs (bulk actions, inline multi-column sort/filter without a page reload) genuinely outgrow query-param-driven server filtering — at that point a data-grid library is a scoped, well-justified addition, not a default.

### ADR-042 — One `articles` table serves both editorial guides and study-abroad content; no separate content-type tables (Phase 12)
- **Problem:** docs/19's Phase 12 scope names two things that read as distinct content types — "articles/guides with source metadata, last-verified dates, intake, disclaimers, review-due queue" and country/city/university-scoped study-abroad content — and docs/05 §3.2 lists only `articles`/`article_sources` in its content-module table inventory, without saying whether study-abroad writeups are a different shape.
- **Options:** (a) two tables — a plain `articles` table for career/general guides and a `study_abroad_guides` table carrying the extra `countryIso2`/`universityId`/`disclaimerKind`/`appliesToIntake` fields docs/12 §14 requires; (b) one `articles` table with those study-abroad-specific columns nullable, distinguished at read time by whether `countryIso2`/`universityId`/`disclaimerKind` are set, not by a type discriminator.
- **Trade-offs:** (a) mirrors the two-hub information architecture (docs/22 §2: Career hub vs. Study Abroad hub) and keeps each table's columns fully populated, but forks every future content feature (search, the review-due queue, the admin CRUD UI, the sitemap's guide entries) into two near-identical code paths for what is, functionally, the same lifecycle (draft → sourced → published → periodically re-verified). (b) keeps one lifecycle, one admin list, one publish gate and one sitemap entry, at the cost of a handful of always-nullable columns on a career guide that never sets them.
- **Decision:** (b). `articles` carries `categoryTermId`/`countryIso2`/`universityId`/`sourceType`/`sources`/`disclaimerKind`/`appliesToIntake` on every row; a career guide (e.g. "How to prep for a system-design interview") simply leaves the study-abroad-specific columns null, exactly as `mentor_affiliations` already leaves `companyId` or `universityId` null depending on `kind` (docs/05's own established pattern for "one table, a few kind-dependent nullable columns" rather than a subtype table per kind).
- **Reason:** The two content "types" never actually diverge in lifecycle or in what the review-due queue, publish gate, or sitemap need to do with them — only in which optional fields are populated — so a type discriminator would add a distinction without a corresponding behavioural difference anywhere in the code.
- **Revisit when:** a genuinely different lifecycle shows up for one kind of content and not the other (e.g. community-contributed guides needing a moderation queue career guides don't) — at that point splitting by behaviour, not by the nullable-column pattern alone, would be justified.

### ADR-043 — Landing pages compose `profiles`/`content`'s existing public functions directly in each page's loader; no new "landing" application layer, and the indexability threshold is computed live per request (Phase 12)
- **Problem:** docs/22 §10.6's programmatic-page quality rule ("indexable only with ≥ 1 verified mentor or ≥ 1 guide or upcoming event, plus an editorial intro") needs a country/city/university/category page to know, on every request, whether it has real content — and that answer spans two modules (`profiles` for mentor counts, `content` for guide counts) that neither module should import from the other to answer.
- **Options:** (a) add a new `landing` (or extend `content`) application-layer module that both `profiles` and `content` feed a denormalised, precomputed "indexable + mentor count + guide count" row per country/university/category, refreshed by a background job whenever a mentor or guide changes; (b) have each landing page's own Server Component loader call `profiles.searchMentors(...)` and `content.countPublishedArticles(...)` directly (both already public, already used elsewhere — `mentors/page.tsx` and `guides/page.tsx`) and compute the threshold inline, on every render.
- **Trade-offs:** (a) would make `generateMetadata`'s `robots` decision and the sitemap's inclusion check both O(1) reads instead of a handful of queries per page/entry, which matters once mentor/university counts are in the thousands — but it's a new module, a new job, and a new "is this in sync with the mentor/guide it's derived from" invariant to maintain, for a launch-scale dataset (docs/00 §9: India + Germany wedge, low hundreds of universities and mentors) where the extra queries are milliseconds. (b) adds no new module and can never drift from the source data (there is no cache to invalidate), at the cost of a handful of `searchMentors`/`countPublishedArticles` calls per page render and, more visibly, inside `sitemap.ts`'s per-type generators, which run the same per-entry checks across every country/city/university/category to decide what belongs in the sitemap.
- **Decision:** (b), matching this codebase's standing preference (ADR-041, and Phase 6–11's search/listing pages generally) for query-time composition over precomputed aggregates until an actual performance need is demonstrated. `sitemap.ts`'s `generateSitemaps` output is cached by Next per docs' own file-convention notes (statically optimized unless it reads request-time data, which none of these generators do), so the per-entry query cost is paid at build/revalidation time, not per visitor.
- **Reason:** Two independent modules, a handful of small aggregate queries, and zero new state to keep synchronised is a better trade at this dataset size than a new module whose only job is caching an answer the two existing modules can already give directly.
- **Revisit when:** the number of countries × cities × universities × categories the sitemap/metadata generators sweep grows large enough that build-time sitemap generation becomes slow, or a page's `generateMetadata` call becomes a measurable request-time cost — at that point a precomputed indexability table (refreshed the same way `mentor_search_documents` already is, per Phase 6/10's `recomputeListingEligibility`) is the natural next step, not a rewrite.

### ADR-044 — `sitemap.ts` uses `generateSitemaps` split by content type; `robots.ts` lists every per-type sitemap URL directly rather than relying on an auto-generated combining index (Phase 12)
- **Problem:** docs/22 §10.4 describes "`/sitemap.xml` index → `sitemap-static.xml`, `sitemap-mentors-N.xml`, ..." — language that reads as "a sitemap index file at `/sitemap.xml` that lists the others," matching how `sitemap.xml` index files conventionally work. The installed Next docs (`node_modules/next/dist/docs/.../sitemap.md`) describe `generateSitemaps` as splitting a sitemap into files served at `/.../sitemap/{id}.xml`, but never state that Next also auto-generates a combining `/sitemap.xml` index once `generateSitemaps` returns more than one id — and a local build/dev smoke test confirmed it: `/sitemap.xml` 404s once `generateSitemaps` is exported, while `/sitemap/0.xml` through `/sitemap/6.xml` all serve correctly.
- **Options:** (a) hand-write a second, literal `sitemap.xml` **index** file (the `<sitemapindex>` XML format, distinct from the `<urlset>` format `sitemap.ts` itself returns) as a route handler, to get a real `/sitemap.xml` URL matching docs/22's literal path; (b) list every per-type sitemap URL (`/sitemap/0.xml` … `/sitemap/6.xml`) directly in `robots.ts`'s `sitemap` field, which accepts a string array — search engines discover all of them from `robots.txt` either way, without needing a literal index file at `/sitemap.xml`.
- **Trade-offs:** (a) matches docs/22's illustrative path literally and gives one canonical URL to hand-submit to Search Console, but means hand-rolling XML `<sitemapindex>` generation as a plain Route Handler (bypassing the `sitemap.ts` file convention entirely, since that convention is claimed by the per-type generator) and keeping a second list of sitemap URLs in sync with `sitemap.ts`'s own `KINDS` array. (b) needs no XML hand-rolling and shares one `KINDS` array (exported from `sitemap.ts`, imported by `robots.ts`) as the single source of truth for how many sitemaps exist and what they're called.
- **Decision:** (b). `sitemap.ts` exports `KINDS`; `robots.ts` imports it and maps each entry to its `/sitemap/{index}.xml` URL. Search Console and crawlers that read `robots.txt`'s `Sitemap:` lines (the documented discovery mechanism robots.md itself describes) find every per-type sitemap this way without a combining index file existing at all.
- **Reason:** `robots.txt` already is the standard discovery mechanism for multiple sitemaps (it explicitly supports repeated `Sitemap:` lines), so a hand-built index file would be solving an already-solved problem for the sake of matching one illustrative path name in the docs, at the cost of a second, hand-maintained list of sitemap URLs.
- **Revisit when:** a specific tool or workflow (e.g. a Search Console property verification step) is found to require a literal `/sitemap.xml` index URL rather than accepting multiple `Sitemap:` lines in `robots.txt` — at that point option (a)'s hand-written index becomes worth the duplication.

### ADR-045 — `FakeGateway` gets chaos-injection knobs (`delayMs`/`failOnce`) and the payment sweeper isolates per-intent failures, instead of building a separate chaos-testing harness (Phase 13)
- **Problem:** docs/13 §1 names "chaos-style tests (provider timeouts, webhook delays)" as a required test layer, but nothing in the payments module lets a test simulate a slow or failing provider call — `createFakeGateway(executor)` takes no configuration — and writing that first chaos test immediately surfaced a real gap: `sweepExpiredPaymentIntents`'s loop had no per-intent error isolation, so one `fetchPaymentStatus` failure would throw out of the whole batch, leaving every other expired intent in that tick unprocessed until the next scheduled run.
- **Options:** (a) build a separate chaos-testing harness/framework (e.g. a proxy layer or test-only gateway wrapper) that intercepts calls to any `PaymentGateway` implementation; (b) add optional `delayMs`/`failOnce` fields directly to `createFakeGateway`'s existing factory signature, consumed by a small `chaosGate()` helper each method calls before doing its real work.
- **Trade-offs:** (a) would be reusable if a second gateway adapter existed, but nothing does yet (docs/19 Phase 8 deviations: only `FakeGateway` is built, a real Razorpay adapter needs live test-mode keys this environment doesn't have) — building generic chaos-injection infrastructure for one implementation is speculative. (b) is a small, direct extension of the one adapter that actually exists, with zero new abstraction, and every call site that doesn't pass `chaos` behaves exactly as before (the parameter defaults to `{}`).
- **Decision:** (b). `FakeGatewayChaos` (`delayMs?`, `failOnce?: Partial<Record<method, boolean>>`) is threaded through `createFakeGateway` and (as an optional third parameter) `sweepExpiredPaymentIntents`; `failOnce` auto-resets after firing once so a test can assert "one failed attempt, then a normal recovery" without extra bookkeeping. The sweeper's loop body is wrapped in a per-intent `try/catch` that increments a new `failed` count on `SweepResult` and moves on — a skipped intent stays `pending` and is naturally retried by the next tick's `listExpiredPendingIntents` re-select, so nothing is lost, only delayed.
- **Reason:** The chaos tests this phase needed to write (`tests/integration/payments/chaos.test.ts`: a provider outage during checkout rolling the whole attempt back, a slow-but-successful checkout, a webhook that never arrives being recovered by the sweep, and one intent's failure not blocking the rest of a sweep batch) all became straightforward once the fake gateway itself could simulate the failure modes being tested, and the sweeper bug they surfaced was worth fixing immediately rather than filing away — a production incident (one bad provider response stalling a whole sweep tick) that chaos testing exists specifically to catch.
- **Revisit when:** a second real `PaymentGateway` adapter is built (Phase 16+, a real Razorpay integration) — at that point, whether chaos-injection knobs belong on every adapter or purely on `FakeGateway` (with the real adapter chaos-tested via a recorded-fixture proxy instead) is worth a fresh look.

### ADR-046 — Lighthouse budgets run via the plain `lighthouse` package against Playwright's own Chromium, not `@lhci/cli`; SEO and Performance scores are measured but not yet gated (Phase 13)
- **Problem:** docs/13 §9 requires Lighthouse CI budgets (Performance ≥ 90, Accessibility ≥ 95, SEO ≥ 95, Best Practices ≥ 95) but nothing wires Lighthouse into this repo yet, and there is no staging/preview deployment to run it against (docs/19 Phase 16). The obvious first choice, `@lhci/cli`, turned out to pull in a stale `lighthouse`/`puppeteer-core` chain whose `extract-zip`/`tmp` transitive dependencies carry real high-severity CVEs (symlink path traversal, arbitrary file write) — confirmed via `npm audit --audit-level=high`, which would have broken the existing, already-green `security` CI gate the moment `@lhci/cli` was added.
- **Options:** (a) accept `@lhci/cli`'s vulnerable transitive dependencies and either weaken the audit gate (`--omit=dev`) or add a blanket ignore; (b) use the plain `lighthouse` npm package directly, driven over CDP against a Chromium instance Playwright itself launches (`chromium.launch({args: ["--remote-debugging-port=9222"]})`), since `@playwright/test` is already a dependency and its browser management doesn't route through `extract-zip`/`tmp` at all.
- **Trade-offs:** (a) is less code (no custom runner script) but means either accepting real, currently-exploitable-in-principle high-severity findings into the dependency tree, or quietly loosening a security gate this session has otherwise kept strict all along — both worse than the problem being solved. (b) needed a ~90-line runner script (`scripts/perf/lighthouse-budgets.ts`) but `npm audit --audit-level=high` confirmed the plain `lighthouse` package (current release, pinning `puppeteer-core@^25` and `@puppeteer/browsers@3.x`, which replaced `extract-zip`/`tmp` with `modern-tar`) adds zero new findings.
- **Decision:** (b). The script also measures Performance and SEO every run but only gates Accessibility and Best Practices for now: Performance, because shared CI runners are known to throttle unpredictably under Lighthouse's simulated-mobile conditions and this is the first time it's ever been measured here (no historical baseline to set a real threshold against); SEO, because a local run confirmed every non-production environment's deliberate `X-Robots-Tag: noindex` + `robots.txt Disallow: /` (a real safety feature, not a bug) drags the SEO category from a high-90s score down to the mid-60s via Lighthouse's heavily-weighted "is-crawlable" audit — gating on that here would be gating on the safety net working correctly, not on real page quality.
- **Reason:** A security-conscious dependency choice and an honest test gate matter more than saving ~90 lines of runner code, and a budget gated on noise (an untuned CI-performance threshold, or a score that's structurally wrong in every non-production environment) is worse than no gate at all — it trains everyone to ignore red.
- **Revisit when:** either a staging environment exists (docs/19 Phase 16) to measure a meaningful SEO score against, or enough nightly Performance data has accumulated to set a real threshold — at which point both become hard gates, not just reported numbers.

### ADR-047 — A generated route inventory + CI diff-gate ships now; the full per-actor BOLA matrix docs/13 §5 describes is an explicit carry, not attempted in one pass (Phase 13)
- **Problem:** docs/13 §5 wants a generated test suite enumerating every route (137 `route.ts` files, 155 method entries) against every actor type (anonymous/owner/other student/other mentor/moderator/staff-without-MFA/staff-with-stale-session/etc.), gated so "a new route without matrix entries fails the build" — and today none of that exists: authorization is tested ad hoc, per feature, with no shared actor-factory helper and no route inventory of any kind (confirmed by a full repo search before starting).
- **Options:** (a) hand-write the full actor × route response matrix for all 155 route entries in this pass; (b) build the generator + CI-gate mechanism first — a script that statically walks every `route.ts`, extracts its `defineRoute` name/actor-mode and whether an `authorize()`/`requireStaff`/`requireAnyRole`/`requireRecentUserAuth` call is visible in the file, writes it to a committed JSON snapshot, and a test that fails the build the moment a fresh regeneration drifts from that snapshot — without attempting the full per-actor assertion matrix in the same pass.
- **Trade-offs:** (a) would be the complete, docs-literal mechanism, but writing correct, non-flaky expected-response assertions for 155 route entries — including standing up the right actor fixtures (restricted user, staff without MFA, staff with a stale session, moderator vs. finance vs. admin, owner vs. stranger) for routes this session hasn't touched — is a multi-day undertaking on its own, not a same-phase addition to everything else Phase 13 already built; a half-finished matrix that only covers a handful of routes while implying full coverage would be actively misleading (this project's standing "never overstate what's built" rule). (b) is honestly scoped to what a single pass can actually finish and verify: the generator was proven correct against a real bug (an initial version mis-attributed the wrong route's `name`/`actor` to a POST when a file declared multiple `defineRoute` calls — caught by ESLint's `no-unused-vars` flagging the broken lookup, fixed, and re-verified against every multi-method file), and the gate was proven to actually fire by temporarily adding a fake route and watching the test fail with the exact diff before removing it.
- **Decision:** (b). `scripts/authz/generate-route-inventory.ts` + `tests/authz/route-inventory.json` (committed) + `tests/authz/route-inventory.test.ts` (the CI gate) ship this phase. The `hasVisibleAuthzCall` field is documented as a best-effort static signal, not a guarantee — 16 of 155 entries resolve an actor but show no direct `authorize()` call in the route file itself, and spot-checking confirmed all 16 are legitimate (public read routes, or `/me/*` routes scoped by the caller's own `userId` in the query rather than a role check), not silent authorization bugs.
- **Reason:** Shipping a real, working, honestly-scoped half of the mechanism — one that makes every future route change impossible to land without a human looking at it — is better than either skipping it entirely or claiming a matrix that doesn't actually assert per-actor expectations yet.
- **Revisit when:** a dedicated pass (this phase's retrospective names it as the natural next Phase 13/14 increment) builds the actor-factory helper (`tests/helpers/actors.ts`-style, producing the 9 actor kinds docs/13 §5 lists) and fills in real per-route expected-response assertions — starting with the highest-value routes (step-up-gated admin mutations, cross-user resource access) rather than all 155 at once.

### ADR-048 — Nightly/weekly CI split for the checks that don't belong on every PR; ZAP's first run doesn't fail the build yet (Phase 13)
- **Problem:** docs/13 §11 wants concurrency-test repeats, the full multi-browser E2E suite, Lighthouse, ZAP and a deep OSV-Scanner sweep, but none of these belong on every PR — concurrency repeats alone (25× over 9 tests) and 5-browser E2E would multiply `ci.yml`'s runtime many times over for marginal per-PR value, and ZAP/OSV need either a running build or extra tooling this repo's PR gate shouldn't pay for on every push.
- **Options:** (a) add everything to the existing `ci.yml` behind conditionals; (b) two new scheduled workflows — `nightly.yml` (concurrency repeat ×25, full 5-browser/device E2E, Lighthouse budgets — all daily) and `weekly.yml` (OSV-Scanner deep scan, ZAP baseline — both weekly), each with `workflow_dispatch` for on-demand runs, alongside a lighter PR-time addition (OSV-Scanner joins `npm audit` in `ci.yml`'s existing `security` job, since it's fast and dependency-only).
- **Trade-offs:** (a) keeps everything in one file but couples unrelated concerns (a fast PR gate vs. slow/flaky-prone nightly sweeps) and makes `ci.yml` harder to reason about. (b) mirrors docs/13 §11's own "PR / nightly / weekly" cadence directly in the workflow structure, at the cost of two more files to keep in sync with `ci.yml`'s shared env block.
- **Decision:** (b), plus one deliberate posture choice for the very first ZAP run: `fail_action: false`. This is the first time ZAP has ever scanned this app — there's no `.zap/rules.tsv` triage file yet to separate real findings from baseline-scan noise, and Phase 14 ("Security review") is explicitly where docs/19 says findings get triaged and fixed. Failing the workflow on an untriaged first scan would either hide the check behind an immediately-red, permanently-ignored badge, or force a rushed triage under this phase's scope rather than Phase 14's. The scan still runs weekly and files/updates a tracking GitHub issue (`allow_issue_writing: true`) so findings are visible now, just not blocking yet. `osv-scanner.toml` (repo root) documents the one accepted exception both the PR-time and weekly OSV-Scanner runs share (the same dev-only `drizzle-kit`/esbuild finding `npm audit --audit-level=high` already excludes by severity threshold — docs/21 note in `security` job history), with the same reasoning recorded inline as `.gitleaksignore` already does for its own exceptions.
- **Reason:** A gate that's known to be noisy on day one and gated anyway just gets muted or force-merged past, which is worse than an honest "measured, not yet gated" posture with a clear trigger for when it tightens.
- **Revisit when:** Phase 14 triages the first few weeks of ZAP findings into a real `.zap/rules.tsv` allowlist — at that point `fail_action: true` becomes the honest default, not a false claim of a gate that would immediately need to be silenced.

### ADR-049 — The ASVS 5.0 checklist is built from the real, freshly-fetched spec text, scoped to L1/L2 with chapter-grouped evidence rather than a per-item deep-dive for every one of 253 requirements; findings are triaged live rather than dumped into one big list (Phase 14)
- **Problem:** docs/11 §12 names `docs/security/asvs-l2-checklist.md` as a Phase 14 deliverable, verified against "OWASP ASVS 5.0 Level 2" — but ASVS 5.0 is a large, versioned, actively-maintained external standard (17 chapters, 253 Level-1/2 requirements), and this session's own training data could plausibly be stale or misremember 5.0-specific renumbering versus earlier ASVS versions (4.x chapters and numbering differ meaningfully from 5.0's). Getting the requirement text wrong would make every "Met"/"Not Met" judgment built on top of it unreliable.
- **Options:** (a) write the checklist from memory of ASVS's general shape, accepting the risk of citing a requirement that doesn't actually exist in 5.0 or misreading its level; (b) fetch the actual current ASVS 5.0 chapter files directly from the `OWASP/ASVS` GitHub repository before writing anything, extract every Level 1/2 requirement's real ID and wording programmatically, and ground every checklist row in that extracted text.
- **Trade-offs:** (a) is faster but the entire point of an ASVS-verification deliverable is that it verifies against the *actual* standard — a checklist built from a possibly-imprecise memory of the standard isn't meaningfully different from an unstructured "here's what I think is secure" writeup, just dressed up with ASVS-shaped section numbers. (b) costs 17 fetches and some extraction scripting up front, but every requirement ID and level cited in the resulting document is provably real, not reconstructed.
- **Decision:** (b). A short Python extraction pass pulled every Level 1/2 requirement (253 total) into per-chapter reference files before any checklist writing began. Within each chapter, the checklist groups closely-related items (e.g. "6.2.6–6.2.8: `type=password`, paste/password-manager allowed, no truncation" as one row) rather than one row per numbered sub-requirement where several map to the same piece of evidence — full requirement text is in the upstream spec, not reproduced verbatim here; what the checklist adds is the status and the evidence pointer, and cramming near-duplicate rows for items with identical evidence would make the real findings harder to find, not easier. Three genuine bugs were found and fixed *during* the walkthrough rather than just recorded (§0 of the checklist): a bare-SHA-256 key derivation (11.4.4), an unredacted email in a log call (16.2.5), and a stale code comment claiming a security control existed that never did.
- **Reason:** An ASVS checklist's value is entirely in its accuracy against the real standard and the real code — grouping related items for readability doesn't weaken that (the underlying evidence is still item-specific where it differs), but citing a wrong requirement ID or level would have. Fixing findings live, where cheap and safe (no production data at stake yet), is worth more than a longer list of deferred items with the same content.
- **Revisit when:** ASVS 5.1 (or later) is released, or before the external penetration test docs/11 §12 gates on live money — at that point the checklist should be regenerated against the new spec text the same way, not hand-patched.

### ADR-050 — Bookings record when they were first confirmed; the late-capture sync only ever touches never-confirmed bookings (Phase 15a)
- **Problem:** Found while seeding demo data through the real services: `syncPaidBookingsOnce` treated *every* `cancelled_by_student`/`cancelled_system` booking with a succeeded payment as "the capture arrived after the hold was abandoned" and orphaned it for a full refund. That set also contains bookings that were confirmed normally and cancelled later — whose refund the cancellation policy had already decided. The sync relabelled them `payment_orphaned` and attempted a second refund (which failed on the ledger's over-refund guard), and for a 0% late cancellation it would have refunded 100%, bypassing the published policy. Separately, `cancellation.student.courtesy_late_cancels_per_90d` was never read: the courtesy check hard-coded one per 90 days.
- **Options:** (a) derive "was ever confirmed" at sync time from the audit trail; (b) keep a `confirmed_at` column on `bookings`, set by every path that confirms, and filter on it; (c) compare the payment's capture time with the cancellation time.
- **Trade-offs:** (a) couples money-moving logic to audit-log contents and string action names. (c) is racy and wrong for seats the system cancels. (b) costs one column and a backfill, and states the fact the sync actually needs.
- **Decision:** (b). `bookings.confirmed_at` is set when a booking is inserted as confirmed (free bookings and seats) and by `transitionBookingStatus` on the first transition to `confirmed` (`coalesce`, so re-confirmation never moves it). A check constraint requires it for `status = 'confirmed'`. Migration `0014` backfills it from `booking.confirmed`/`session.seat_registered` audit rows, falling back to `created_at` for statuses only reachable through `confirmed`. The sync lists only bookings with `confirmed_at IS NULL`, and `confirmPaidBooking` independently refuses to orphan a booking that has it (defence in depth). The courtesy check now reads its setting. Both fixes have regression tests that fail without them (`tests/integration/payments/paid-booking-lifecycle.test.ts`).
- **Reason:** A refund path must never be able to overrule the refund policy; the cheapest robust guard is a persisted fact, not an inference.
- **Revisit when:** a booking can legitimately return to `confirmed` from a state that already settled money (e.g. dispute reversal flows) — `confirmed_at` would then need a companion "settled" marker.

### ADR-051 — Signed-in pages read through Server Components and a request-memoised viewer; the browser mutates only through the REST API; the public header learns who is signed in from a 200-always probe (Phase 15a)
- **Problem:** Phase 15 builds the first signed-in student/mentor UI. It has to respect ADR-019 (every mutation through a `defineRoute` handler — no Server Actions), keep public pages static/ISR for performance and SEO, and compose read models (mentor cards, session lists) that span modules no single module owns.
- **Options:** (a) client-rendered app pages that fetch everything from the JSON API; (b) Server Components that read module APIs directly, with client components only for interaction; (c) (b) plus Server Actions for forms.
- **Trade-offs:** (a) doubles round trips, needs loading states for every read and adds API surface for read models. (c) contradicts ADR-019's single audited mutation path. (b) keeps reads fast and server-side while every write still passes CSRF, validation, rate limits, idempotency and audit in one place.
- **Decision:** (b). Pages call `requireViewer(path)` (`src/server/views/viewer.ts`, memoised per request with React `cache()`, redirecting to `/sign-in?returnTo=…`); the redirect lives in pages because layouts don't know the path. Cross-module read models live in `src/server/views/*`, composed only from module public indexes (the architecture test's rule). Client components use `src/ui/api.ts`, which adds idempotency keys and turns problem+json into a typed `ApiError` with field errors; sensitive calls go through `useReauth`, which answers `REAUTH_REQUIRED` with an in-place password (and 2-step) prompt, then retries. The public header is a client island calling `GET /api/v1/auth/viewer`, which returns `{ viewer: null }` with 200 for anonymous visitors, so signed-out page views log no failed requests and public pages stay statically rendered. `GET /auth/me` keeps its correct 401 contract. New write endpoints: `PATCH /me/account`, `POST /auth/verify-email/resend`, `POST /auth/sessions/:id/revoke`.
- **Reason:** Reads where the data is; writes through the one path that is already secured, tested and audited.
- **Revisit when:** the static GitHub Pages preview (Phase 15e) needs a build-time persona in `requireViewer`, or if Cache Components are adopted (the `revalidate` exports on home/events would move to `"use cache"`).

### ADR-052 — Demo data is created through the application services, never inserted as rows (Phase 15a)
- **Problem:** The UI needs realistic data to design against and to show in the preview: mentors with verified affiliations, completed sessions with reviews, upcoming paid bookings, events with registrations, guides.
- **Options:** (a) SQL fixtures inserting rows directly; (b) a script that drives the real services — sign-up, the mentor application and staff approval, email-challenge verification, booking, fake-gateway checkout and its signed webhook, check-ins, attendance claims and the finaliser — "time-travelling" by passing explicit `now` values.
- **Trade-offs:** (a) is faster to write and run but can silently produce states the product can never reach, and has to be updated by hand whenever invariants change. (b) takes longer to run and write, but every row satisfies the same constraints real data does — and it exercises long multi-step flows no single test had combined.
- **Decision:** (b), as `npm run db:seed:demo` (`scripts/db/seed-demo.ts`, data in `scripts/db/demo/data.ts`). Fictional people only, accounts on `example.com`, queued emails purged, and the script refuses to run when `APP_ENV` is `staging` or `production`. It found both production bugs in ADR-050 on its first full run.
- **Reason:** Demo data that could not have been produced by the product is a liability; data produced by it is also a free end-to-end test.
- **Revisit when:** the seed's runtime becomes a problem for CI (it is local/preview-only today).

### ADR-053 — Checkout confirms through a client-initiated, provider-verified sync of one booking; the fake provider is gated by APP_ENV, not NODE_ENV (Phase 15b)
- **Problem:** Building checkout exposed that a paid booking was only ever confirmed by the scheduled sweep (webhook job, then the booking sync job). docs/08 §6 rule 5 says "the same code path handles client confirmation, webhooks, sweepers and reconciliation", but there was no client-confirmation path at all — students would wait a full scheduler interval. Separately, the fake provider's checkout and webhook routes were disabled whenever `NODE_ENV=production`, which every `next start` build sets, so neither e2e nor a sandbox deployment could take a payment.
- **Options:** (a) process the webhook job inline inside the webhook route; (b) poll `GET /payment-intents/:id` until the next tick; (c) a student-owned `POST /bookings/:id/payment-sync` that re-fetches the provider's record and runs the same capture and settle steps the sweep runs.
- **Trade-offs:** (a) breaks docs/08's "acknowledge fast, process async" rule and still leaves the booking unconfirmed until the booking sync runs. (b) is honest but slow. (c) adds one route but gives an immediate answer grounded only in the provider's own state; it is idempotent with the webhook job, whichever runs second.
- **Decision:** (c). `refreshPaymentForOrderItem` (payments) reuses `applyVerifiedCapture`; `settlePaidBooking` (booking) is now the single per-booking step behind both `syncPaidBookingsOnce` and the new `syncPaidBooking`, which only the booking's own student may call. The checkout calls it after paying and polls it briefly; booking pages still "waiting for payment" call it once on load. The fake routes now check `APP_ENV !== "production"`, and env validation refuses `PAYMENTS_PROVIDER=fake` with `APP_ENV=production`.
- **Reason:** Immediate, trustworthy confirmation without a second code path, and a fake provider that is off exactly where it must be.
- **Revisit when:** Razorpay's checkout handler lands (Phase 16) — its success callback should call the same sync after verifying the handler signature.
